# 05 협업 규칙

- 버전 1.0 (2026-10-22) · PM 희승
- 요약: **이슈로 말하고, 브랜치에서 일하고, PR로 합의하고, 병합은 PM이 한다.** 진행 상태와 작업 시간은 브랜치 · 커밋 · PR로 자동으로 잡힌다.

## 1. 하루 흐름

```
① 내 이슈 고르기 ─▶ ② 브랜치 만들기 ─▶ ③ 작게 커밋·푸시 ─▶ ④ PR 열기 (Draft 가능)
       ▲                                                      │
       │                                ⑤ 리뷰 짝이 리뷰·승인 ◀┘
       └──── ⑦ 이슈 자동 닫힘 ◀── ⑥ PM이 병합 (main)
```

- **매일 최소 한 번은 흔적을 남긴다**: 커밋 푸시, 이슈 댓글, PR 리뷰 중 하나. 이틀 동안 아무 흔적이 없으면 PM 보고서에 "활동 없음"으로 뜬다.
- 막히면 30분 넘게 혼자 붙잡지 말고 이슈에 `status:막힘` 라벨 + 무엇이 막혔는지 댓글. PM과 관련 담당자를 `@`로 부른다.

## 2. 이슈

| 규칙 | 내용 |
|---|---|
| 이슈 = 일의 단위 | 이슈 없이 작업하지 않는다. 할 일이 생기면 먼저 이슈를 만든다 (템플릿 사용) |
| 크기 | 하루~이틀이면 끝나는 크기. 더 크면 나눈다 |
| 담당자 | 반드시 Assignee 지정. 담당자 없는 이슈는 보고서에 뜬다 |
| 마감 | Milestone(관문) 지정 = 마감일 |
| 진행 상태 | 시작하면 댓글 "시작" 또는 Draft PR 연결. 막히면 `status:막힘` |
| 질문 | 연구원님·KTL에 물어볼 것은 **ktl-hub**에 `질문` 라벨 이슈로. 직접 연락하지 않고 PM이 모아서 전달 |
| 계약 변경 | API·QR·모듈 계약·categories.yaml을 바꾸고 싶으면 ktl-hub에 `계약변경` 이슈 |

### 라벨

| 라벨 | 뜻 |
|---|---|
| `type:기능` `type:버그` `type:문서` `type:테스트` | 종류 |
| `우선:필수` `우선:권장` `우선:2차` | 01 요구사항의 M / S / C |
| `status:막힘` | 다른 사람·정보를 기다리는 중 |
| `size:S` `size:M` `size:L` | 반나절 / 하루 / 이틀 |
| `질문` `계약변경` | ktl-hub 전용 |

## 3. 브랜치 · 커밋

- `main`은 보호된다. **직접 푸시 불가**, PR로만 들어간다.
- 브랜치 이름: `<종류>/<이슈번호>-<짧은설명>` — 예: `feat/12-qr-parser`, `fix/31-cp949-bom`, `docs/4-readme`
- 커밋 메시지: `<종류>: <무엇을> (#이슈번호)` — 예: `feat: QR 체크값 검증 추가 (#12)`
  - 종류: `feat` `fix` `docs` `test` `refactor` `chore`
- 작게 자주 커밋하고 **하루 한 번 이상 푸시**한다 (진행 상황이 보고서에 잡히는 기준).
- 커밋 작성자 이메일을 GitHub 계정에 등록된 이메일로 설정한다 (그래야 보고서에서 내 커밋으로 잡힘).
  ```
  git config user.name  "<GitHub 아이디>"
  git config user.email "<GitHub에 등록한 이메일>"
  ```

## 4. PR (Pull Request)

| 규칙 | 내용 |
|---|---|
| 언제 | 이슈 작업을 시작하면 바로 **Draft PR**로 열어도 좋다. 완성되면 "Ready for review" |
| 본문 | 템플릿대로: 관련 이슈(`Closes #12`), 무엇을 바꿨나, 어떻게 확인했나, 스크린샷 |
| 크기 | 리뷰 가능한 크기 (변경 400줄 안쪽 권장). 크면 나눈다 |
| 리뷰 | **리뷰 짝 승인 1개 필수** ([04 역할분담](04-역할분담.md)의 리뷰 짝). 계약 파일을 건드리면 영향받는 파트 담당자도 |
| 리뷰 기한 | 리뷰 요청을 받으면 **24시간 안에** 승인 또는 의견 |
| CI | `data-guard`(실데이터 차단)와 테스트가 통과해야 한다 |
| **병합** | **PM(희승)만 병합한다.** 승인 받았으면 PR에 "병합 요청" 댓글 + `@didgmltmd`. 다른 사람은 병합 버튼이 막혀 있다 |
| 병합 방식 | Squash merge (이슈 1개 = main 커밋 1개) |
| 충돌 | PR 올린 사람이 `main`을 받아 해결 |

### 리뷰할 때 보는 것

1. 이슈의 완료 기준을 만족하는가 (요구사항 ID)
2. 계약(API·QR·모듈)과 맞는가
3. 실제 데이터·실명·비밀번호가 들어가지 않았는가
4. 인터넷 요청(외부 URL·CDN)이 없는가
5. 실행 방법이 README에 있는가

의견은 "이렇게 바꿔 주세요"보다 **"왜"**를 같이 쓴다. 사소한 것은 `nit:`로 시작해 막지 않는다.

## 5. 진행 상태 · 작업 시간 (자동)

진행 상태와 작업 시간은 **자동으로 잡힌다.** 버튼을 누르거나 따로 기록하지 않아도 된다. 대신 아래 이름 규칙은 꼭 지킨다.

| 이렇게 하면 | 자동으로 |
|---|---|
| 브랜치를 `feat/12-설명`처럼 이슈 번호로 만든다 | 이슈 12가 **진행 중** (GitHub 이슈에 `status:진행중` 라벨) |
| 커밋 메시지에 `(#12)` | 이슈 12의 작업으로 집계 |
| PR 본문에 `Closes #12` | **리뷰 중** (`status:리뷰중`) → 짝 승인 시 **병합 대기** → PM 병합 시 **완료**(이슈 자동 닫힘) |
| 진행 중인데 2일 넘게 커밋·PR이 없다 | PM 현황판에 **멈춤**으로 표시 |

- 작업 시간은 커밋 시각으로 계산한다 (2시간 안에 이어진 커밋을 한 작업으로 본다). 그래서 **작게 자주 커밋·푸시**하는 것이 중요하다.
- 직접 남기고 싶으면 이슈 댓글에 `/time 1.5h 무엇을`을 써도 된다 (선택). PM 보고서에 따로 합산된다.
- 막히면 협업 사이트 이슈 화면의 **⛔ 막혔어요**, 물어볼 게 있으면 **🙋 PM에게 도움 요청**.

## 6. 데이터 · 보안

- **실제 견본 파일(CSV·사진·xlsx·txt), 실명, 업체명, 연구원님 이름은 절대 커밋하지 않는다.** 공개 레포다.
- 테스트 파일은 가짜 값으로 만들어 `synthetic/` 또는 `tests/fixtures/synthetic/` 아래에만 둔다.
- CI `data-guard`가 다음을 막는다: `synthetic/` 밖의 데이터 파일(csv·xlsx·xlsm·jpg·png·txt 등), 진짜처럼 보이는 접수번호.
- 견본 원본은 각자 PC의 레포 **밖** 폴더에 둔다 (`.gitignore`에 `real/`, `samples/`가 있지만 믿지 말 것).
- 실수로 올렸으면 **바로 PM에게 말한다.** 커밋을 지워도 기록에 남으므로 PM이 처리한다.

## 7. 소통 채널

| 무엇 | 어디 |
|---|---|
| 일 이야기 (진행, 질문, 결정) | GitHub 이슈·PR 댓글 — 기록이 남아야 함 |
| 급한 연락, 회의 일정 | 카카오톡 단톡방 → 결정된 내용은 이슈에 옮겨 적는다 |
| 문서 변경 | ktl-hub PR |
| 주간 정리 | 매주 월요일 PM 보고서 기준으로 10분 점검 |
